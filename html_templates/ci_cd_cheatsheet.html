GitLab CI + runner vs Bamboo

For this repo, the validator is simple. The real question is which platform already has a working execution path.

Layer check

These are not the same layer

A GitLab runner is the worker that executes jobs. Bamboo is the CI system that defines plans and sends work to agents. The real comparison is GitLab CI plus runner versus Bamboo plus agent/plugin setup.

Repo scope

No artifact build, no deploy stage, no long dependency chain

Dimension GitLab CI + Runner Bamboo
Config lives in .gitlab-ci.yml in the repo Bamboo plan config, usually in Bamboo Specs YAML or Bamboo UI
Worker model GitLab runner picks up jobs Bamboo agent runs the plan, often with container plugins
Simplest case A shared Docker-capable runner already exists and can run this repo with no extra coordination Your org already has a Bamboo project, linked repo pattern, agent capacity, and approved container/runtime pattern
Typical repo-side effort Very low. One small YAML file can run the validator. Moderate. You need a plan, permissions, repo linkage, agent/runtime choices, and trigger setup.
Typical infra blockers No runner, paused runner, wrong tags, or runner cannot handle image:-based jobs No linked repo, no Bamboo agent capacity, missing permissions, missing image credentials, or webhook plumbing not finished
Where jobs usually fail first Scheduling: the job never starts Setup: the plan exists but repo linkage, agent execution, or container auth is incomplete
Operational ownership Runner team or group-level GitLab CI admins Bamboo admins plus whoever owns linked repos, credentials, and permissions
Branch / MR ergonomics Usually cleaner if the org already trusts GitLab CI as the first-class path Fine once established, but often involves more org-specific conventions
Best fit for this repo Best if a runner already exists Best if Bamboo is the standard paved road and GitLab runners are uncertain
Fast answer Simple in the repo. Not simple if runner infra is missing. Heavier upfront. Predictable if Bamboo infrastructure is already normalized.
Rule of thumb: if a compatible GitLab runner already exists, GitLab is the lighter path. If it does not, Bamboo can be the simpler operational path even though the config surface is larger.
Choose GitLab

Use GitLab when

  • A runner already exists at the project or group level.
  • The runner is online and supports container-style jobs or has the needed tools preinstalled.
  • You want the entire CI definition to stay close to the repo in one small YAML file.
  • You want the lowest repo-side ceremony for a validator-only workflow.
If the runner is already there, this is probably the shortest path.
Choose Bamboo

Use Bamboo when

  • Your organization already treats Bamboo as the standard CI control plane.
  • GitLab runners are unreliable, unavailable, or controlled by another team with slow turnaround.
  • You need Bamboo-native permissions, linked repositories, or existing internal container patterns.
  • You want to align with nearby repos that already use Bamboo conventions.
If GitLab runner availability is the main uncertainty, Bamboo may be easier to get approved.
Questions

What to ask for GitLab

  • Is a runner attached to this project or parent group?
  • Is it online and permitted to pick up jobs?
  • Does it accept untagged jobs?
  • If not, what exact tags are required?
  • Does it support image:-based execution?
  • If no runner exists, who will own and maintain one?
Questions

What to ask for Bamboo

  • Which Bamboo project should own the plan?
  • How will Bamboo link to the GitLab repository?
  • Which Bamboo agents can run the job?
  • Will the job run directly on the agent or inside a container plugin/runtime?
  • If a private image is used, what credentials will pull it?
  • Who sets plan permissions and any webhook trigger wiring?

validate-skills:

Minimal Bamboo Shape

More moving parts

plan:
  project-key: ...
  key: ...
  name: ...

job:
  - checkout repo
  - choose agent/runtime
  - pull image if needed
  - run: bash scripts/validate-all-skills.sh
  - set permissions
  - wire triggers
Bottom line for this repo: the validator is already simple. Do not optimize the YAML shape first. Optimize for the platform that already has a real worker behind it.
