00 // Core Principle
Shape First. Cache Second. Parallelize Third.

Token waste and latency compound -- every round trip that returns verbose data costs twice. Fix the shape of what you return before optimizing how often or how fast you return it. The Atlassian APIs are generous with verbosity; the MCP layer is where you enforce discipline.

01   Tokens
01 // Token Economy -- Overview
Token Economy

Every byte returned from the Atlassian API that reaches the context window costs tokens. Jira issue payloads are wide by default; Confluence storage format is pathologically verbose. The goal is a lean projection layer that delivers exactly what the model needs and nothing else.

Deployed
Tight Field Projection
jira_search defaults to minimal field list -- key, summary, status, assignee, priority. Broad issue shape only on explicit request.
Deployed
Binary Size Gating
Oversized attachments and images are refused for inline return. Protects both server and context window from giant payload blowout.

01B // Pipeline
Candidates
ADF / Storage → Markdown
Convert Atlassian Document Format and Confluence storage XML to clean Markdown before it hits the context. Raw ADF for a medium Confluence page is 5-10x the token count of its Markdown equivalent.
Candidate
Custom Field Resolution
Cache the Jira field metadata endpoint (customfield_10024 → "Story Points"). Remap or filter field keys transparently -- the model should never see opaque field IDs.
Candidate
Account ID Resolution
Every issue response is littered with accountId: "557058:abc...". Keep an in-process accountId → displayName map. Resolve transparently. Cuts "who is this person" follow-ups.
Candidate
Diff-Aware Page Edits
For Confluence updates, model sends (section_id, new_content) instead of full body. Server fetches current, splices change, writes back. Avoids model emitting thousands of tokens it didn't change.
Candidate
Confluence Lazy Sections
For large pages, return structural TOC (headings + section word counts) first. Model requests specific sections by heading. Avoids loading pages the model doesn't actually need.
Candidate
02   Speed
02 // Speed + Latency -- Overview
Speed + Latency

MCP round trips are synchronous from the model's perspective -- every blocked tool call stalls the chain. The surface area for wins: fewer API calls (composite tools, caching), faster API calls (parallelism, connection reuse), and smarter cache invalidation (webhooks over TTL guessing).

02A // Shipped
Deployed
Central HTTP Layer
Auth, proxies, redirects, same-origin checks, bounded retries in one client. Eliminates inconsistent slow-path behavior across tools.
Deployed
Server-Side Pagination
Confluence attachment walks happen once inside the service. Model doesn't rediscover pagination behavior across repeated calls.
Deployed
Optional Live Probes
Startup auth probes available when needed but local users don't pay extra probe traffic every session startup.
Deployed
Early Diagnostics
Readiness, scope, auth mode, and profile state exposed upfront. Broken envs fail fast instead of burning tool calls discovering the problem mid-chain.
Deployed
02B // Pipeline
Candidates
Parallel Fanout
Composite tool handlers fire multiple Jira/Confluence requests concurrently via asyncio.gather. get_issue_full(key, include=["comments","transitions"]) -- one tool call, 3 parallel API requests, single response.
Candidate
Pagination Cursor Cache
On first JQL search, fetch and cache the full result set server-side. Return a cursor/handle. Subsequent pages are served locally, no re-hit to Jira. Especially useful for long result scans.
Candidate
Webhook Cache Invalidation
Register Jira/Confluence webhooks for issue_updated / page_updated events. Invalidate cache entries immediately on change. Makes aggressive TTLs viable without stale data risk.
Candidate
JQL Validation Pre-Flight
Validate JQL against Jira's autocomplete endpoint before firing the search. Return a structured error with suggestions on bad syntax. Eliminates retry round trips on malformed queries.
Candidate
Connection Pool Tuning
aiohttp ClientSession with explicit keepalive limits and connector pool sizing. Atlassian Cloud supports persistent connections. Cold-start penalty on tool call 1 should not repeat on call 2.
Candidate
03   Tools
03 // Tool Design + Architecture
Tool Shape + Novel Patterns

The tool schema is part of the optimization surface. Poorly shaped tools force the model into sequential chains that could be parallelized, or return more than necessary because the caller has no way to ask for less. These patterns address tool design as a first-class concern.

03A // Composite Pattern
Issue Graph Tool

get_issue_tree(key, depth=2) walks Epic → Stories → Subtasks in parallel requests and returns a compact hierarchy. Replaces 3-5 sequential tool calls with one. The model gets the whole picture in a single context addition.

get_issue_tree("PROJ-1", depth=2)
// returns: {epic: {...}, stories: [{...subtasks}]}
// 1 tool call = N parallel API requests
03B // Hierarchy
Confluence Page Tree

get_page_tree(page_id, depth=2) returns title + word count for the subtree. Model decides which pages are worth fetching before loading content. Avoids loading pages it doesn't need. Pairs well with lazy section loading.

get_page_tree("123456", depth=2)
// returns: [{title, id, word_count, children}]
// model requests sections by id after scanning tree
03C // MCP Primitives
Resource URIs

Return MCP resource URIs (confluence://SPACE/page-title) instead of inline content for large pages. Clients that support resource subscriptions get change notifications without polling. Proper use of the MCP resource model vs cramming everything into tool results.

03D // Delta Pattern
Response Diffing

For polling / watch scenarios ("tell me when this issue changes"), store a snapshot on first fetch. On subsequent calls, return only the delta -- changed fields, new comments, status transitions. Cuts token waste on repeated polls to near-zero when nothing changed.

// call 1: full issue snapshot, cached
// call 2: {changed: {status: "In Progress"}, new_comments: 1}
// call 3: {changed: {}, new_comments: 0} -- "no change"
03E // Exploration
FastMCP Source Mining

FastMCP's tool registration, schema generation, and middleware pipeline are worth reading closely. Hook points for pre/post-processing exist in the handler chain -- that is the right place to insert projection, caching, and ADF conversion layers without cluttering individual tool implementations.

  • Tool middleware -- intercept before/after handler for caching + projection
  • Schema inference -- see what FastMCP auto-generates vs what to override
  • Lifespan hooks -- right place for session-scoped caches and connection pools
  • Context object -- per-call state without global mutation

05 // Notes to Self
Server-Side Pagination
Codex-generated pattern -- the service walks Confluence attachment pages internally so the model never rediscovers pagination. Worth fully understanding: how is state held across calls? Is it session-scoped or per-call? Could be a cursor/handle pattern.
Scoped Query Shaping
Deployment filters inserted without breaking trailing ORDER BY. Understand how the JQL is parsed and where the filter injection happens -- this is a fragile surface if the parser is naive string manipulation vs actual AST.
