The Interface Message Processor, widely credited as the world's first packet-switching router, was the specialized minicomputer - a ruggedized Honeywell DDP-516 - that BBN built to sit between each ARPANET host and the leased phone lines connecting the network together, starting in 1969. IMPs talked to their local hosts using a documented, published interface (BBN Report 1822); how IMPs talked to each other across the network's internal links was BBN's own implementation detail, and was never published as a specification the way 1822 was. Every host on the ARPANET connected to its local IMP, and every IMP connected to one or more other IMPs over leased common-carrier circuits, store-and-forwarding packets hop by hop until they reached the destination host's IMP. That basic shape - hosts talk to a local switch, switches talk to each other - is the direct ancestor of every router-based network since.

This station is named for the IMP-to-IMP link protocol specifically, and the most accurate thing this page can tell you about it is that it was never published as an open specification the way the Host-IMP interface (BBN Report 1822) was - hosts needed 1822 to connect at all, so BBN had to document it; the IMP subnet's internal link protocol was BBN's own implementation detail, and reconstructing its exact bit layout from public sources wasn't possible at the confidence bar this site holds itself to. Rather than fabricate a byte diagram for that specifically, the Leader Fields tab documents the adjacent structure that genuinely is well-sourced: the fields of the 1822 Host-IMP leader that determined how a packet got addressed and routed in the first place.
what did carry between IMPs, reliably documented: a Ready-For-Next-Message (RFNM) control message, sent back to the originating host once a message had been fully delivered to its destination - the ARPANET's flow-control primitive, and conceptually a distant ancestor of a TCP ACK, though nowhere near as fine-grained.

The original Host-IMP leader was 32 bits; a host's full network address was split across two small fields inside it. Only the fields independently confirmed across multiple sources are diagrammed here - the leader's remaining bits (message type, handling flags, padding) aren't reconstructed since this page can't confirm their exact positions.

what a "link" was for. A host could have several logical connections open to the same remote host at once (e.g. a control connection and a data connection) - the link number, not the destination address, was what a receiving host used to sort incoming messages onto the right one. Later ARPANET protocols (NCP, then the transport-layer half of what became TCP) inherited this same idea of a small in-band multiplexing field, decades before TCP/UDP port numbers made it a universal concept.

The IMP concept - dedicated switches doing the packet-forwarding work so host computers don't have to - proved durable even as the ARPANET itself aged out.

yeareventwhy it mattered
1969first IMP installed at UCLA, followed within months by SRI, UCSB, and the University of Utahthe original 4-node ARPANET - the network this whole legacy section is about.
1970Heart, Kahn, Ornstein, Crowther, and Walden publish "The Interface Message Processor for the ARPA Computer Network"the primary published description of the IMP's design - still the best public source on how it worked internally.
1975the "long leader" 1822 format replaces the original short leaderIMP numbers grew from 6 to 16 bits and host numbers from 2 to 8 - the original address space was simply running out as the network grew past its first few dozen nodes.
1983the ARPANET's NCP-to-TCP/IP flag dayevery host switched from the ARPANET-specific Network Control Program to TCP/IP on the same day - the event most historians point to as "the internet" beginning in earnest.
1989the ARPANET is formally decommissionedby then its function had been fully absorbed into the wider, IMP-free internet - the specialized switch-computer this page is about had already been replaced by general-purpose routers running open protocols.
