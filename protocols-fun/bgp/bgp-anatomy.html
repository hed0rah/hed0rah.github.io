Every other protocol on this site is a fixed header used by every host on the internet. BGP (RFC 4271, 2006) is used by only a few tens of thousands of routers - and it's the reason any two of those routers can find each other at all. It runs as a long-lived session over plain TCP port 179 (see the TCP anatomy page), which means BGP itself never had to solve reliable delivery, retransmission, or ordering - just what to say once connected. Unlike TCP, BGP's own version number genuinely changed four times before freezing in 1994; unlike TCP, nobody has ever needed a wire-format-preserving rewrite like RFC 9293, because BGP-4's header hasn't needed one. versionspecyearwhat changed
BGP-1RFC 11051989the original - path vector routing between autonomous systems, replacing EGP
BGP-2RFC 11631990refinements to the original exchange
BGP-3RFC 12671991further refinement - still classful, no prefix-length concept yet
BGP-4RFC 1654 → RFC 1771 (1995) → RFC 4271 (2006)1994classless interdomain routing (CIDR) - NLRI became prefix + length instead of classful network numbers. The version number has not moved since.

Everything since 1994 - route refresh (RFC 2918, 2000), multiprotocol/IPv6 support (RFC 2283 → RFC 2858 → RFC 4760, 1998-2007), 4-octet AS numbers (RFC 6793, 2012) - shipped as new capabilities and attributes layered on top of the same BGP-4 header, never a version bump. Same pattern as TCP's Options field absorbing 40 years of change without touching its fixed header.

headerMarker + Length + Type, 19 bytesspecRFC 4271

Every BGP message, regardless of type, opens with the same 19 bytes. The Marker is a holdover from an authentication scheme BGP-4 never actually specified in detail - in practice it's always all-ones today.

generic message header (19 bytes)
why BGP has no inherent trust model. Any TCP peer that completes an OPEN exchange can originate routes for any prefix, for any AS - BGP believes what its neighbors tell it. In April 1997, a misconfigured router belonging to a small ISP (AS 7007) re-originated a huge share of the internet's routing table as if it owned it, causing a widespread multi-hour outage - still one of the most-cited incidents in networking history. RPKI origin validation and BGPsec (RFC 8205, 2017) exist to add real cryptographic trust, decades later, and remain unevenly deployed.
type1size43 bytes with 2 capabilities

The first message on a new session - negotiates the AS numbers, hold timer, and (via Optional Parameters) every capability both sides support before a single route is exchanged. This example negotiates both a 4-octet AS number and IPv6 route support in one OPEN.

OPEN, with capabilities (43 bytes)

My AS is 23456 (AS_TRANS) - a placeholder, because the real AS (400000) doesn't fit in the 2-byte field. See the AS Numbers tab.

capability code65specRFC 6793 (2012), obsoletes RFC 4893

Original BGP-4 AS numbers are 16 bits - a 65,536-AS ceiling the internet was on track to hit. RFC 6793 widens the field to 32 bits, but only where both peers agree to it via the capability negotiated in OPEN; a peer that doesn't understand 4-octet AS numbers has to see something in the 2-byte AS_PATH field regardless, which is exactly what the reserved placeholder AS 23456 ("AS_TRANS") is for.

the same AS_SEQUENCE entry, two widths

One AS (this page's example numbers: 64512 for the 2-byte case, 400000 for the 4-byte case) inside an AS_PATH segment.

old attribute kept, new one added alongside. Rather than redefining AS_PATH itself, RFC 6793 introduces two new optional transitive attributes - AS4_PATH (type 17) and AS4_AGGREGATOR (type 18) - that a 4-octet-capable router attaches alongside the classic ones. A router that doesn't understand 4-octet AS numbers just ignores these extra attributes and keeps working with AS_TRANS in the field it does understand - the same "old peer stays functional, new peer gets more" pattern as TCP Options or DHCP's magic cookie.
type2size45 bytes, 1 route announced

The message that actually carries routes - both withdrawals and announcements can appear in the same UPDATE, though this example has only an announcement. Path attributes are BGP's own TLV format, distinct from the option encodings on every other protocol on this site.

UPDATE announcing 203.0.113.0/24 (45 bytes)

ORIGIN, AS_PATH, and NEXT_HOP are the three attributes every route announcement must carry.

capability code1attributeMP_REACH_NLRI, type 14lineageRFC 2283 → 2858 → 4760

BGP-4's original UPDATE format is IPv4-only - the withdrawn-routes and NLRI fields at the end assume 4-byte prefixes. Multiprotocol Extensions (RFC 4760) didn't redesign UPDATE to fix this - it added two new optional attributes, MP_REACH_NLRI and MP_UNREACH_NLRI, that carry routes for any address family (IPv6, VPNs, multicast) entirely alongside the untouched classic format. This is the actual mechanism that lets BGP route IPv6 at all.

keepalivetype 4, header onlynotificationtype 3, tears down the session

KEEPALIVE is the smallest possible BGP message - just the 19-byte header, sent periodically (a third of the Hold Time, by convention) to prove the session is still alive without waiting for an actual route change. NOTIFICATION is BGP's only error-signaling message, and sending or receiving one always closes the TCP connection - there's no "soft" BGP error.

KEEPALIVE (19 bytes - the header, and nothing else)
NOTIFICATION, Cease / Administrative Reset (21 bytes)

RFC 4486 added the finer-grained Cease subcodes (like Administrative Reset) - the base NOTIFICATION format itself hasn't changed since BGP-4.
