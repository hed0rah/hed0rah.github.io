UDP Anatomy

RFC 768 (1980)
rev 2026.08
header 8 bytes, always
checksum optional in v4, mandatory in v6
variant UDP-Lite, RFC 3828

RFC 768 (August 1980, Jon Postel) is one of the shortest RFCs that anything on the internet still runs on - three pages, and it has never been revised or obsoleted the way TCP's spec was. The entire protocol is four 16-bit fields: source port, destination port, length, checksum. No connection state, no retransmission, no ordering - whatever reliability a UDP-based application wants, it builds itself on top. The one genuine wrinkle: the checksum is optional over IPv4 and mandatory over IPv6 - same field, different rule, and it's easy to miss if you only ever tested on one address family. Every example on this page is a DNS query, 192.0.2.10:51234 (IPv4) / 2001:db8::1a2b:3c4d:5e6f (IPv6) → port 53 on 203.0.113.5 / 2001:db8::1, matching the addressing conventions already used on the TCP page and in ipv6-fun. header8 bytes, no exceptionsspecRFC 768

Same port-pair idea as TCP, same 16-bit fields - but that's where the resemblance ends. There's no flags byte, no window, no options, because there's no connection to manage.

source & destination ports (4 bytes)

A DNS query: client ephemeral port 51234 to server port 53.

size8 byteschecksumoptional (RFC 768)

Over IPv4, a sender may set the checksum to all-zeros to mean "I didn't compute one" - the receiver then skips verification entirely. This was a real performance shortcut in 1980; almost nothing does it deliberately today, but it's still legal.

UDP header over IPv4 (8 bytes)

Same DNS query, 4-byte placeholder payload. Checksum computed over a 12-byte IPv4 pseudo-header (source, destination, zero, protocol=17, UDP length) plus the full segment.

size8 bytes, identical shapechecksummandatory (RFC 8200 §8.1)

RFC 8200 removes the option: over IPv6, a UDP sender must compute a real checksum. If the computed value happens to come out as exactly zero, it has to be transmitted as all-ones (0xFFFF) instead - zero is reserved to mean "not computed," a meaning IPv6 doesn't allow UDP to claim.

UDP header over IPv6 (8 bytes)

Identical ports and payload to the IPv4 tab - the checksum comes out different purely because the pseudo-header is IPv6's (32-byte addresses, no protocol/zero bytes the same way) instead of IPv4's.

protocol number136 (not 17)specRFC 3828 (2004)

A distinct sibling protocol, not a UDP option - it gets its own IP protocol number (136) specifically so routers and middleboxes never confuse it with ordinary UDP. Built for real-time media (VoIP, video) where a corrupted payload is still more useful than no payload at all: it lets a receiver accept a segment even if part of it fails the checksum, as long as the part it cares about didn't.

UDP-Lite header (8 bytes, same shape as UDP)

Same ports and payload again - only the meaning of bytes 4-5 changes.

the one field that changes. UDP's Length field becomes UDP-Lite's Checksum Coverage Length: the number of bytes, starting from the UDP-Lite header itself, that the checksum actually protects. A value of 0 means "cover everything" (ordinary UDP behavior); any other value must be at least 8 - a receiver seeing 1 through 7 must discard the packet outright, since that would cover less than the header itself.
