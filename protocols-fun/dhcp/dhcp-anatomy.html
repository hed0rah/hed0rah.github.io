DHCP (RFC 2131, 1997) didn't invent its own wire format - it's built directly on BOOTP's 1985 header, kept wire-compatible enough that a DHCP server can still answer plain BOOTP clients. The 236-byte fixed header is diagrammed here up through the 16-byte client hardware address; two legacy BOOTP fields after it - a 64-byte server name and a 128-byte boot filename, both usually all-zero today - are skipped rather than drawn 192 times over. A DHCPDISCOVER - the very first message, broadcast by a client that has no address and no idea which server (if any) will answer.

Every address field is still 0.0.0.0 at this stage - the client doesn't have one, doesn't know the server's, and there's no relay agent on this segment. The broadcast flag is set because a client with no IP configured yet can't reliably receive a unicast reply.

Same 8-10 byte position, two different fields entirely. BOOTP's original spec leaves it simply unused; DHCP claims it for the broadcast flag. Everything before and after this point in the fixed header is identical between the two.

bytes 8-9: BOOTP (1985)
bytes 8-9: DHCP (1997)
what else changed. BOOTP's vendor-specific area (the bytes after the fixed header) is a fixed 64 bytes, and RFC 951 only recommends starting it with a 4-byte magic number - it's optional. DHCP inherited the magic-cookie-prefixed option format from RFC 1497's BOOTP vendor extensions, made the cookie mandatory, and - critically - made the whole options area variable-length instead of capping it at 64 bytes. That variable-length options area is where DHCP message types, lease times, and every other DHCP-specific behavior actually live; none of it required touching the fixed header at all.
