PPP (Point-to-Point Protocol, RFC 1661/1662) wraps every packet in a thin HDLC-derived envelope - a flag byte, an address and control byte that are always the same fixed values, a 2-byte protocol field, the payload, and a real CRC. Before any actual data flows, both ends negotiate the link itself using LCP (Link Control Protocol), which rides inside that same envelope as just another protocol value. Address and Control are always the same two bytes on a PPP link - HDLC's addressing and numbered-mode machinery were designed for multi-drop links PPP never uses, so PPP just fixes them at their "all-stations, unnumbered" values and moves on.

full frame (22 bytes)
the FCS is a real, computed CRC-16/X-25. Written in Python against RFC 1662's exact algorithm (poly 0x1021/reflected 0x8408, init 0xFFFF, input and output reflected, XOR-out 0xFFFF) and self-checked against the standard's own published test vector (ASCII "123456789" → 0x906E) before being run against this frame's actual bytes - not filled in by hand. Transmitted least-significant byte first, per RFC 1662 §C.2.
code1 (Configure-Request)optionsMRU, Magic-Number

This is the Information field from the Overview tab's frame, zoomed in. Every LCP packet shares this Code+Identifier+Length shape - and so does PAP, CHAP, and every NCP (IPCP, IPv6CP) that configures a specific network-layer protocol on top of the same link.

LCP packet (14 bytes)
self-describing options, not a fixed schema. Because every option carries its own Type and Length, a station can send options an older peer doesn't recognize - the peer just skips the bytes it doesn't understand (or Configure-Rejects the specific option) rather than failing to parse the whole packet. The same TLV idea shows up in IPv6 extension headers and DHCP options elsewhere on this site.

PPP's HDLC-derived framing survived the death of dial-up entirely - it's still exactly what runs inside PPPoE on most consumer DSL connections today.

eraeventwhy it mattered
1970sIBM's SDLC, generalized into ISO's HDLCthe flag-byte-delimited, CRC-checked framing this whole page is built on.
1988SLIP (RFC 1055) - Serial Line IPthe thing PPP replaced: no header, no protocol field, no error detection, no link negotiation - it could only ever carry IP, and only ever assumed both ends already agreed on everything out of band.
1994PPP (RFC 1661) and PPP-in-HDLC-like-framing (RFC 1662)real link negotiation (LCP), authentication (PAP/CHAP), and multi-protocol support (a Protocol field, so IP, IPX, and AppleTalk could all ride the same dial-up link) - genuinely general-purpose where SLIP was a hack.
1999PPPoE (RFC 2516) - PPP over EthernetISPs kept PPP's per-user authentication and accounting model when they moved customers from dial-up modems to always-on DSL, by tunneling the same PPP frames inside Ethernet instead of a serial line.
todayPPPoE still runs on a large share of consumer DSL/fiber connectionsthe HDLC envelope and LCP negotiation this page diagrams are, right now, running underneath a real percentage of home internet connections that have never seen an actual telephone modem.
