RFC 826 (1982) - resolves an IPv4 address to a link-layer (MAC) address by broadcasting the question to the entire segment. The format is deliberately hardware/protocol-agnostic (that's what the length fields are for), but Ethernet+IPv4 is the pairing that ever mattered in practice, so that's the 28-byte layout every tab here uses. There's no authentication anywhere in this protocol - anyone on the segment can answer any question, which is the entire basis of ARP spoofing. IPv6 replaced this mechanism outright with multicast-based Neighbor Discovery rather than patching it; see ipv6-fun's coverage of NS/NA. "Who has 192.0.2.1? Tell 192.0.2.10." The target hardware address is unfilled - that's exactly what's being asked for.

ARP Request (28 bytes)
size28 bytessentunicast, straight back to the requester

"192.0.2.1 is at 00:aa:bb:cc:dd:ee." Sender and target fields swap roles compared to the request - the answerer's address is now the "sender," the original asker is now the "target."

ARP Reply (28 bytes)
size28 bytestellsender protocol addr = target protocol addr

A host announces its own mapping unprompted - nobody asked. Used to pre-populate everyone else's cache after booting or changing MAC (fewer stale-cache misses), or defensively to detect a duplicate address (if something else replies "that's mine," you have a conflict). The functional ancestor of gratuitous NDP Neighbor Advertisements - same idea, same lack of any authentication to stop someone else from doing it maliciously.

Gratuitous ARP (28 bytes)

Structurally just an ARP Request where the sender already knows the answer.

oper3 (request) / 4 (reply)statusobsolete - replaced by BOOTP/DHCP

Reverse ARP (RFC 903, 1984): a diskless workstation that knows its own MAC but not its IP broadcasts to ask the reverse question ARP normally answers. Same 28-byte shape, same field meanings - the asker just repeats its own MAC in both the sender and target hardware fields, since it's asking about itself.

RARP Request, historical (28 bytes)
replaced, not patched. RARP had real limits - no way to hand out anything besides an IP address, and it required a server on every physical segment since RARP requests don't route. BOOTP (RFC 951, 1985) replaced it, and DHCP (RFC 2131, see the DHCP anatomy page) then extended BOOTP rather than replacing it a second time.
