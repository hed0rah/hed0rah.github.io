Every other protocol on this site is a fixed C-struct-shaped header. SNMP (RFC 1157, 1988) isn't - it's ASN.1 encoded using BER (Basic Encoding Rules), which means every field is self-describing: a one-byte tag says what it is, a length byte says how many bytes follow, then the value - and values can nest other tag-length-value groups arbitrarily deep. A SEQUENCE (tag 0x30) is BER's version of a struct; an INTEGER (0x02), OCTET STRING (0x04), and OBJECT IDENTIFIER (0x06) are its primitives. This page's SNMPv1 example has every length verified against its actual encoded content, not just asserted. Hover a field to light its bytes, click a field marked + for its lookup table.

The PDU shape barely changed across twenty years - v2c mostly just added GetBulkRequest and richer error codes on top of v1's format. Security is where the real revision happened, and it happened once, all at once, in v3.

versionauthenticationmessage shape
v1a plaintext "community string" sent with every request - anyone who can sniff the wire has full read (or write) accessversion + community + PDU, exactly like the GetRequest tab
v2csame community-string model as v1 - the "c" stands for "community," not "secure"same shape as v1, plus new PDU types (GetBulkRequest, InformRequest)
v3real per-user authentication (HMAC-MD5/SHA) and optional encryption (DES/AES) via the User-based Security Model (USM)a much larger msgGlobalData + msgSecurityParameters header wraps a scopedPDU - not just a bigger version number on the same envelope
why this page doesn't diagram v3 byte-by-byte. SNMPv3's USM security header is a genuinely different, much larger structure (authoritative engine ID, engine boots/time, username, and authentication/privacy parameters, all before the actual PDU is even reachable) - accurately encoding one requires far more BER nesting than a GetRequest does. It's a real candidate for its own page later; for now, the honest summary above beats a rushed, unverified byte diagram.
