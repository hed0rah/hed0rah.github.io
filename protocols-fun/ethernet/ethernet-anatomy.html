Ethernet II is the frame format almost everything above it - IPv4, ARP, IPv6 - actually rides on. Two 6-byte MAC addresses, a 2-byte field that tells the receiver what's inside, then payload. It's the field at byte 12 that has the messiest history: DIX Ethernet (1980) used it as an EtherType; the original IEEE 802.3 standard (1983) used the identical bit position as a Length field instead, and the two only stopped colliding because IEEE reserved every value large enough to be a valid EtherType. The fixed part of every Ethernet II frame: destination address, source address, then the field that decides what the payload is. Payload (46-1500 bytes) and the trailing FCS aren't diagrammed here - see the Preamble/FCS tab for the checksum.

Exact same 2-byte position, byte 12-13, two incompatible meanings. IEEE 802.3's original framing had no EtherType-equivalent at all - the payload itself had to start with an 802.2 LLC header to say what protocol it carried, an extra layer of indirection Ethernet II never needed.

bytes 12-13: DIX Ethernet II (EtherType)
bytes 12-13: IEEE 802.3 original (Length)
how a receiver tells them apart. A real payload can be at most 1500 bytes, so IEEE reserved every value of this field from 1536 (0x0600) upward exclusively for EtherType use - a length can never legally reach that high. RFC 894 (1984) formally defines EtherType-framed IP; RFC 1042 (1988) defines the alternative for 802.3/LLC networks. EtherType framing won in practice - the length-framed/LLC path survives mainly for a handful of legacy protocols like Spanning Tree BPDUs.
tagIEEE 802.1Q, 1998insertedbetween source MAC and EtherType

A VLAN-tagged frame gets 4 extra bytes spliced in right after the source MAC: a fixed TPID announcing "a tag follows," then a Tag Control Information field packing a priority, a drop-eligibility bit, and a 12-bit VLAN ID into 16 bits.

TPID (2 bytes)
TCI: PCP, DEI, VID (16 bits)
why TPID reuses the EtherType position. TPID sits in exactly the byte-12 slot an untagged frame's EtherType would occupy, using the reserved value 0x8100 - so a switch that doesn't understand 802.1Q would misread it as "EtherType 0x8100," see an unrecognized value, and typically drop the frame rather than silently misparse it. The real EtherType (0x0800 for IPv4, etc.) is pushed 4 bytes later, right after the TCI.

Neither of these is part of the "frame" an operating system ever sees - the NIC generates the preamble/SFD on transmit and strips them on receive, and generates/verifies the FCS the same way. They're shown here because they're genuinely part of what goes on the wire.

The FCS shown is a real CRC-32 (the same algorithm gzip, PNG, and PKZIP use) computed over the 18 bytes above, packed least-significant-byte first the way it's actually captured on the wire - which is also why it reads "backwards" compared to every other multi-byte field on this page: Ethernet transmits ordinary data least-significant-bit-first, but the FCS's most significant bit first, a quirk baked into IEEE 802.3 since 1983. A real frame pads its payload to 46 bytes minimum (64 bytes total before the FCS) - this example is intentionally short to keep the diagram readable.

The 14-byte header diagrammed in the Overview tab has been untouched since 1980 - every revision below changed speed, medium, or added optional fields, never the core frame shape.
