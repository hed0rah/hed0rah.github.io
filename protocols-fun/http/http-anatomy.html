HTTP/1.1 (RFC 9112) is the rare protocol whose wire format you can read with your eyes - a request or response is just ASCII text, lines separated by CRLF, headers separated from the body by a blank line. HTTP/2 (RFC 9113) threw that out entirely for a binary, length-prefixed frame format built to multiplex many requests over one TCP connection. Both are diagrammed here byte by byte. methodGETspecRFC 9112 §3

A minimal HTTP/1.1 GET request: a request line, one header, and the blank line that ends the header block. Every byte here is printable ASCII - there is no separate "header" structure at the wire level, just text with a rigid grammar.

request line + Host header (37 bytes)
why Host became mandatory. RFC 1945's HTTP/1.0 had no Host header at all - a request carried no way to say which site on a shared IP address it wanted, which is why name-based virtual hosting didn't exist yet. RFC 9112 makes Host mandatory on every HTTP/1.1 request; a server MUST reject a request that lacks one with 400 Bad Request.
status200 OKspecRFC 9112 §4

The status line mirrors the request line's shape: version, a space-delimited code, and a human-readable reason phrase that's purely cosmetic - clients are required to key behavior off the numeric code, never the phrase text.

status line + Content-Length header (39 bytes)
reason phrases are decoration. RFC 9112 explicitly allows a server to send any reason phrase, or an empty one, without changing meaning - "200 OK" and "200 " are equally valid. Everything a client does with the response is driven by the 3-digit code alone.
use casebody length unknown up frontspecRFC 9112 §7.1

When a server can't compute Content-Length ahead of time - a dynamically generated response, a live stream - it sends the body as a series of chunks, each prefixed by its own size in hex, ending with a zero-length chunk.

chunked body: "Hello" in one chunk, then terminator (15 bytes)
request smuggling lives here. A message that somehow has both a Content-Length and a Transfer-Encoding header lets a front-end proxy and a back-end server disagree about where the body ends - each may trust a different header. RFC 9112 §6.1 mandates rejecting or stripping such messages precisely because HTTP/1.1's text framing gives an attacker two competing ways to say "how long is this body."
frame typeHEADERS (1)specRFC 9113 §4.1

Every HTTP/2 frame opens with this same 9-byte header, no matter its type. There is no text left anywhere in the framing layer - length, type, and flags are raw binary, and headers themselves get compressed with HPACK before being carried as frame payload.

generic frame header, all types (9 bytes)
flags byte, HEADERS frame type
what multiplexing actually buys. Every frame is tagged with a stream ID, so a client can have dozens of requests in flight on one TCP connection and the server can interleave DATA frames from all of them in any order - solving the head-of-line blocking that forced HTTP/1.1 clients to open six-plus parallel TCP connections per origin just to load a page in parallel.

The one true wire-format break in HTTP's history is 1.1 to 2 - everything before that added headers, methods, and caching semantics onto the same text grammar; HTTP/2 replaced the grammar itself.

versionspecwhat changed on the wire
0.91991, no RFC - described after the facta single line: "GET /path". No version token, no headers, no status line - the response was raw document bytes and the connection just closed.
1.0RFC 1945 (1996)added the version token, a status line, and headers - but no Host header, and one request per TCP connection by default.
1.1RFC 2068/2616 (1997/1999), respecified as RFC 7230-7235 (2014) and RFC 9110-9112 (2022)mandatory Host header, persistent connections by default, chunked transfer encoding, pipelining (rarely used in practice) - still the same CRLF text grammar throughout every respec.
2RFC 7540 (2015), respecified as RFC 9113 (2022)binary framing, one TCP connection multiplexing many streams, HPACK header compression - the format this page's HTTP/2 Frame tab diagrams.
3RFC 9114 (2022)keeps HTTP/2's framing concepts but moves transport from TCP to QUIC over UDP, eliminating TCP-level head-of-line blocking between streams.
the pattern. HTTP/0.9 through 1.1 is one 23-year lineage of the same text grammar getting more rules bolted onto it. HTTP/2 didn't extend that grammar - it replaced the framing layer outright and pushed HPACK compression underneath, while keeping the same methods, status codes, and header semantics a browser already understood.
